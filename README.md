# AI-помощник для подготовки товарных описаний (КИП)

Прототип сервиса, который по данным о контрольно-измерительном приборе
формирует черновик карточки товара для B2B-интернет-магазина: SEO-заголовок,
SEO-описание, ключевые характеристики, поисковые запросы и коммерческий блок
для менеджера.

Работает с облачными и локальными LLM: OpenAI, Anthropic, Google, OpenRouter,
Groq, DeepSeek, Ollama, LM Studio и другими. Провайдер и модель задаются
в настройках, смена провайдера не требует правок кода. Ключ хранится только
в переменных окружения / `.env`, который исключён из Git.

---

## Возможности

- Приём данных о товаре в формате JSON (CLI) или через веб-форму.
- Один вызов LLM со структурированным JSON-ответом.
- Автоматический fallback режимов JSON: `json_schema` → `json_object` → JSON в промпте.
- Проверка лимитов: заголовок ≤ 70 символов, описание 800–1200 символов,
  3–5 поисковых запросов.
- Защита от выдуманных характеристик: цифры и единицы сверяются с входом,
  каждая характеристика привязана к исходному ключу `specs`.
- Автоматический repair-цикл, если ответ не прошёл проверку.
- Явный список отсутствующих данных (`missing_fields`) и значений, требующих
  уточнения (`needs_clarification`).
- Вывод в JSON, Markdown или обычный текст.
- Веб-форма и JSON API.

## Быстрый старт

Все команды выполняются **из корня проекта** — папки, где лежит этот `README.md`.

Требуется Python 3.11+ (проверено на 3.14.5). Проверить версию:

```bash
python --version
```

Если команда `python` не найдена: в Windows попробуйте `py -3`, в Linux/macOS — `python3`.

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Если PowerShell блокирует активацию (`running scripts is disabled`), выполните
один раз в текущем окне:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

Либо не активируйте окружение, а вызывайте интерпретатор напрямую:
`.\.venv\Scripts\python.exe -m app.cli ...`.

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

### Настройка `.env`

Откройте `.env` и **обязательно замените** `LLM_API_KEY` и `LLM_MODEL`:

```env
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=sk-...
LLM_MODEL=gpt-4o-mini
LLM_TIMEOUT=60
LLM_TEMPERATURE=0
LLM_MAX_TOKENS=2000
LLM_JSON_MODE=auto
LLM_MAX_REPAIRS=1
```

Без валидного ключа команды `--check` работают (LLM не нужен), а генерация
завершится ошибкой конфигурации с подсказкой, что заполнить.

### Проверка установки

```bash
python -m app.cli data/p1_manometr.json --check
```

Ожидаемый вывод — входные данные разобраны, пробелы найдены:

  "manufacturer": "Манотомь",
  "specs_count": 6,

    "питание",

| Провайдер | `LLM_BASE_URL` | Пример `LLM_MODEL` |
|---|---|---|
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| OpenRouter | `https://openrouter.ai/api/v1` | `openai/gpt-4o-mini` |
| Groq | `https://api.groq.com/openai/v1` | `llama-3.3-70b-versatile` |

Для локальных серверов ключ может быть любым (`ollama`, `lm-studio`).

`LLM_JSON_MODE`:

- `auto` — сначала `json_schema`, затем `json_object`, затем JSON в промпте;
- `schema` / `object` / `prompt` — принудительный режим.

### Полностью локальный запуск (без облака и ключей провайдера)

Прототип не требует деплоя, БД или внешней инфраструктуры — достаточно
локальной машины и любого OpenAI-совместимого сервера.

1. Установите LM Studio (или Ollama), загрузите модель и включите сервер:
   в LM Studio — вкладка Developer → Start Server (порт `1234`);
   в Ollama — `ollama serve` (порт `11434`).
2. Пропишите в `.env`:

   ```env
   LLM_BASE_URL=http://127.0.0.1:1234/v1
   LLM_API_KEY=lm-studio
   LLM_MODEL=google/gemma-4-e4b
   ```

3. Проверьте вход и сгенерируйте карточку:

   ```bash
   python -m app.cli data/p1_manometr.json --check
   python -m app.cli data/p1_manometr.json
   ```

Именно так сгенерированы примеры в `examples/` — локальной моделью
`google/gemma-4-e4b`, без облачного API.

## Запуск

### 1. Проверка входных данных без обращения к LLM

```bash
python -m app.cli data/p1_manometr.json --check
```

Выводит количество характеристик и список отсутствующих разделов.

### 2. CLI

```bash
# Markdown в stdout
python -m app.cli data/p1_manometr.json

# JSON в файл
python -m app.cli data/p2_metran.json --format json --out result.json

# Обычный текст
python -m app.cli data/p1_manometr.json -f txt
```

Коды возврата: `0` — успех, `2` — ошибка входных данных, `3` — ошибка
конфигурации, `4` — ошибка LLM или генерации.

### 3. Веб-форма

```bash
uvicorn app.main:app --reload
```

Откройте <http://127.0.0.1:8000> — в форме уже подставлен пример JSON.
Результат можно скопировать одной кнопкой. Остановить сервер — `Ctrl+C`.

Если `uvicorn` не найден, venv не активирован или зависимости не установлены;
альтернатива без активации:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

### 4. JSON API

Linux/macOS:

```bash
curl -X POST http://127.0.0.1:8000/api/generate \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Манометр показывающий DM 02",
    "manufacturer": "Манотомь",
    "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5"}
  }'
```

Windows PowerShell (`curl` здесь — алиас, поэтому используем `Invoke-RestMethod`):

```powershell
$payload = @{
  name = "Манометр показывающий DM 02"
  manufacturer = "Манотомь"
  specs = @{ "диапазон измерений" = "0–1,6 МПа"; "класс точности" = "1,5" }
} | ConvertTo-Json -Depth 4

$bytes = [System.Text.Encoding]::UTF8.GetBytes($payload)
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/generate" `
  -ContentType "application/json; charset=utf-8" -Body $bytes
```

Ошибки: `422` — некорректный вход, `503` — не настроен LLM, `502` — ошибка
провайдера или генерации.

## Контракт результата

| Поле | Описание |
|---|---|
| `seo_title` | Заголовок ≤ 70 символов с пробелами |
| `seo_description` | Сплошной текст 800–1200 символов с пробелами |

## Как это работает

```
JSON товара
   │
   ├─ предвалидация (pydantic): обязательные поля, типы, минимум данных
   ├─ detect_missing_fields: какие группы характеристик отсутствуют
   │
   ├─ system + user промпт ──► LLM (OpenAI-compatible)
   │        ▲                        │
   │        │                        ▼
   │   repair-промпт ◄── валидация ответа:
   │                     • лимиты 70 / 800–1200 / 3–5
   │                     • числа и единицы ⊆ входных
   │                     • source_key и basis ⊆ входных ключей
   │                     • маркеры домыслов и отрицаний
   │
   └─► CardDraft (JSON / Markdown / текст)
```

### Промпты

System-промпт задаёт роль редактора B2B-карточек и жёсткие правила:

1. единственный источник фактов — `INPUT`;
2. запрещено добавлять материалы, сертификаты, гарантию, комплектацию,
   страну производства и прочие отсутствующие свойства;
3. единицы измерения не конвертируются (`0–1,6 МПа` не превращается в `16 бар`);
4. отсутствующая характеристика не упоминается, а попадает в `missing_fields`;
5. маркетинговые формулировки — только пересказ входных фактов;
6. коды и стандарты (`IP65`, `Ex ia IIC T6`, `M20×1,5`) переносятся как есть,
   без расшифровки;
7. деловой нейтральный тон без оценочных обещаний.

User-промпт содержит JSON товара и перечень отсутствующих разделов.

### Защита от выдуманных характеристик

| Проверка | Что делает |
|---|---|
| Числа | Каждое число в заголовке, описании и commercial-блоке должно встречаться во входе |
| Единицы | Единица допускается, только если она есть во входе (и стоит после числа) |
| `source_key` | Характеристика отбрасывается, если её нет во входных `specs` |
| Значение характеристики | Числа/единицы значения должны быть в исходном значении |
| `basis` | Основания commercial-блока сверяются с ключами `specs` или `description` |
| Маркеры домыслов | «нержавеющая», «взрывозащита», «гарантия», «надёжный» и т.п. вне входа → предупреждение |
| Отрицания | «агрессивные» при входном «неагрессивные» → предупреждение об искажении |

Серьёзные предупреждения (домысел, искажение, выдуманные числа/единицы,
некорректный `basis`) запускают repair; лимиты — тоже. Если после
`LLM_MAX_REPAIRS` нарушения остались, результат возвращается с `warnings[]`,
а не падает — контент-менеджер видит, что проверить.

Дополнительно после ответа модели:

- `key_specs` детерминированно дополняется всеми характеристиками из входных
  `specs`, чтобы структурированный список был полным;
- заголовок длиннее 70 символов обрезается по границе слова;
- описание длиннее 1200 символов обрезается по границе предложения или слова;
- список запросов усекается до 5;
- такие автоправки попадают в `warnings[]`.

## Принятые решения

- **Один вызов LLM на карточку.** Все поля генерируются согласованно,
  дешевле и быстрее, чем отдельные вызовы на заголовок и описание.
- **Structured output с fallback.** `json_schema` даёт самый надёжный JSON,
  но не все провайдеры его поддерживают; поэтому есть `json_object` и
  режим «JSON в промпте» с разбором и repair.
- **Частичная генерация при нехватке данных.** Сервис не блокирует работу:
  возвращает карточку только по имеющимся фактам и перечисляет пробелы.
- **Без конверсии единиц в v1.** Это убирает класс ошибок округления и
  делает проверку «числа из входа» однозначной.
- **Детерминированный `missing_fields`.** Список отсутствующих разделов
  считается по словарю синонимов, а не генерируется моделью. Значения
  с пометками «уточнить», «н/д», «?» попадают в `needs_clarification`.
- **Предупреждения не роняют запрос.** Ограничения длины после repair
  отдаются с `warnings`, чтобы MVP не терял результат на живом входе.
- **Ключ только из окружения.** `.env` в `.gitignore`, в репозитории есть
  `.env.example`.

## Если что-то не запускается

| Симптом | Причина и решение |
|---|---|
| `python` не найден | В Windows — `py -3`, в Linux/macOS — `python3`; проверьте PATH |
| `uvicorn` не найден | Активируйте venv или запустите `.\.venv\Scripts\python.exe -m uvicorn app.main:app` |
| `Activate.ps1 cannot be loaded` | `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` или вызывайте `.\.venv\Scripts\python.exe` напрямую |
| `LLM_API_KEY не задан` | Нет `.env` или ключа: `cp .env.example .env`, заполнить `LLM_API_KEY`, `LLM_MODEL` |
| `LLM_API_KEY содержит заглушку` | В `.env` осталось значение `sk-your-key-here` из примера — замените на реальный ключ |
| `401` / `invalid api key` | Неверный ключ или `LLM_BASE_URL` не соответствует провайдеру |
| `404 model not found` | Имя модели не совпадает с тем, что отдаёт провайдер; проверьте `LLM_MODEL` |
| `провайдер не поддерживает ни один режим JSON` | Укажите `LLM_JSON_MODE=prompt` — останется разбор JSON из текста |
| `connection refused` для локальной модели | Не запущен Ollama/LM Studio или другой сервер на `LLM_BASE_URL` |
| Ответ стабильно вне лимитов | Увеличьте `LLM_MAX_REPAIRS` или возьмите более сильную модель |
| `ModuleNotFoundError: multipart` | `pip install -r requirements.txt` (там есть `python-multipart`) |

## Границы решения (раздел 8 ТЗ)

| Ограничение из ТЗ | Что сделано |
|---|---|
| Не требуется CMS, админ-панель, БД или деплой | Ничего из этого не реализовано намеренно: нет БД, ORM, миграций, авторизации, Docker и CI. Результат — файл или HTTP-ответ, состояние между запросами не хранится |
| Не требуется конкретная LLM или векторная база | Провайдер и модель задаются только через `LLM_BASE_URL` / `LLM_MODEL`; по умолчанию подставляется OpenAI-совместимый адрес, но он переопределяется. Векторного хранилища и RAG нет — один вызов LLM на карточку |
| Достаточно локального прототипа по инструкции | `README` → «Быстрый старт» и «Полностью локальный запуск»; проверено на локальной модели LM Studio, примеры сгенерированы без облака |
| Достаточно MVP, остальное — в улучшениях | В README есть раздел «Возможные улучшения»: LLM-as-judge, нормализация единиц, кэш, пакетная обработка, Wordstat, evals, async, Docker |
| Не выдумывать характеристики, явно указывать нехватку | Промпт + проверки чисел/единиц/`source_key` + repair + `warnings`; подробности — в разделах «Промпты» и «Защита от выдуманных характеристик» |

## Ограничения

- Семантические искажения ловятся эвристиками, а не полноценной проверкой
  фактов: сложный перефраз или противоречие без ключевых слов может пройти.
- Если описание получилось короче 800 символов и repair не помог, оно
  возвращается как есть с предупреждением: добивать текст выдуманными
  фактами нельзя.
- Нет конверсии единиц и нормализации (`G1/2` и `G 1/2` считаются разными).
- Поисковые запросы генерируются без частотности — доступа к Wordstat нет.
- Только русский язык.
- Качество зависит от модели; локальные 4–8B модели хуже держат лимиты
  и стиль, чем облачные.
- Запрос синхронный: долгая генерация занимает HTTP-соединение.
- Нет БД, истории, аутентификации, rate-limit и деплоя — по условиям задания.
- `LLM_JSON_MODE=auto` может сделать несколько попыток при неподдерживаемом
  режиме — это влияет на задержку, но не на результат.

## Возможные улучшения

- Второй проход «LLM-as-judge»: проверка, что каждое утверждение подтверждено входом.
- Нормализация единиц и обозначений с сохранением исходного значения.
- Кэширование ответов по хэшу входа и версии промпта.
- Пакетная обработка каталога и выгрузка в CMS/CSV.
- Частотность запросов через Wordstat/Keys.so.
- Few-shot примеры под разные категории КИП и offline-эвалюация на наборе карточек.
- Асинхронные задания и очередь для длинных генераций.
- Docker и минимальная авторизация для внутреннего использования.

## Критерии оценки (раздел 7 ТЗ)

| Критерий | Как закрыт |
|---|---|
| Качество и практическая применимость, а не объём кода | MVP из небольших модулей, запускается по README, есть CLI, форма и API |
| Корректность, читаемость, структура кода | pydantic-схемы, разделение слоёв (`llm` → `validator` → `generator` → `render`), type hints, `ruff check` без замечаний, 48 тестов |
| Качество промпта: точность, устойчивость, соответствие задаче | Роль + жёсткие правила, единственный источник фактов, structured output с fallback, repair-промпт с перечнем нарушений; тесты на содержимое промптов |
| Отсутствие выдуманных технических характеристик | Четыре слоя: промпт, детерминированные проверки чисел/единиц/`source_key`, repair, `warnings`; отбрасывание незаземлённых характеристик |
| Обработка неполных или некорректных данных | `missing_fields`, `needs_clarification`, отказ на пустые обязательные поля, коды возврата CLI, HTTP 422/502/503, тесты на `null` и неверные типы |
| Понятность и готовность результата для контент-менеджера | Markdown с разделами, счётчики `title 59/70` и `description 966/800–1200`, предупреждения и «данных нет», кнопка «Копировать» |
| Качество README и простота запуска | Быстрый старт, таблица провайдеров, примеры команд, troubleshooting, описание решений и ограничений |
