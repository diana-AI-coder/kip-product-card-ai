КАК ВЫПОЛНЕНО ТРЕБОВАНИЕ «ВАЖНО» ИЗ ТЕСТОВОГО ЗАДАНИЯ
========================================================

Формулировка из ТЗ: «не выдумывайте характеристики прибора. Если данных
недостаточно, явно укажите это в результате».

Требование закрыто четырьмя слоями: промпт, детерминированная проверка,
repair-цикл и явный вывод недостающих данных.


1. ПРОМПТ — ЗАПРЕТ КАК ПРАВИЛО, А НЕ ПОЖЕЛАНИЕ
------------------------------------------------
Файл: app/prompts.py, строки 13–18.

- Единственный источник фактов — блок INPUT. Общие знания о модели,
  производителе или типе прибора использовать запрещено.
- Запрещено добавлять характеристики, которых нет во входе: материалы,
  степень защиты, сертификаты, гарантию, страну производства, комплектацию,
  сроки поставки, цену, преимущества без основания.
- Единицы измерения не конвертируются: «0–1,6 МПа» остаётся «0–1,6 МПа»,
  а не «16 бар».
- Если сведений о характеристике нет — она не упоминается, замена не
  придумывается.
- Коды и стандарты (IP65, Ex ia IIC T6, G1/2, M20×1,5) переносятся как есть,
  без расшифровки про пыль, влагу или взрывобезопасность.

Те же ограничения повторяются в пользовательском промпте (prompts.py:61)
и в repair-промпте (prompts.py:91), чтобы модель не «забыла» их при
исправлении ответа.


2. ДЕТЕРМИНИРОВАННАЯ ПРОВЕРКА ПОСЛЕ ОТВЕТА LLM
-----------------------------------------------
Файл: app/validator.py.

- Числа и единицы из результата должны быть подмножеством чисел и единиц
  входных данных (функции _numbers и _units, строки 74–82).
- Каждая характеристика обязана иметь реальный source_key из входных specs
  (validator.py:193). Если ключа нет — характеристика ОТБРАСЫВАЕТСЯ,
  а не просто помечается предупреждением.
- Значение характеристики сверяется с исходным значением этого ключа
  (validator.py:205–228): «0–2,5 МПа» при входном «0–1,6 МПа» не пройдёт.
- Основания commercial-блока (basis) сверяются с ключами specs или со
  значением description (validator.py:258).
- Маркеры домыслов: «нержаве», «гаранти», «взрывозащищ», «надёжн»,
  «долговечн», «сертифи» и т.п. вне входных данных дают предупреждение
  (validator.py:32–57, 238–250).
- Проверка искажения отрицаний: «агрессивные» при входном «неагрессивные»
  или «не являются агрессивными» даёт предупреждение (validator.py:245–250).


3. REPAIR-ЦИКЛ
---------------
Файл: app/generator.py, строки 32–36 и 76.

- Серьёзные предупреждения (домысел, искажение, выдуманные числа/единицы,
  неверный basis) и нарушения лимитов запускают повторную генерацию
  с явным перечнем нарушений.
- Если за LLM_MAX_REPAIRS (по умолчанию 1) нарушения не устранены,
  результат возвращается с заполненным warnings, а не молча и не падением.


4. ЯВНОЕ УКАЗАНИЕ НЕХВАТКИ ДАННЫХ
----------------------------------
- Функция detect_missing_fields (validator.py:130) детерминированно,
  по словарю синонимов, определяет отсутствующие разделы: диапазон
  измерений, класс точности, питание, тип корпуса, степень защиты,
  интерфейсы, присоединение.
- Результат попадает в поле missing_fields (generator.py:118).
- В Markdown и текстовом выводе есть разделы «Недостающие данные»
  и «Предупреждения» (render.py:33, 41), а при пустом списке выводится
  «данных нет» (render.py:19, 26).

ЧЕСТНОЕ ОГРАНИЧЕНИЕ
-------------------
Проверка семантическая лишь частично: это эвристики по числам, единицам,
ключевым словам и отрицаниям, а не полноценный фактчекинг. Сложный перефраз
без ключевых слов может проскочить. Ограничение зафиксировано в README
в разделе «Ограничения», а второй проход «LLM-as-judge» — в разделе
«Возможные улучшения».
